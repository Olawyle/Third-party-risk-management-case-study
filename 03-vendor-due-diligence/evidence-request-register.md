# Evidence Request Register

## 1. Purpose

The Evidence Request Register provides a structured record of the evidence requested from CloudServe Technologies Ltd. to support the Tier 1 enhanced due diligence assessment.

The register is intended to provide traceability between:

**Risk → Control Requirement → Evidence Request → Evidence Review → Finding**

Vendor responses alone will not be considered sufficient evidence where independent or supporting documentation is required.

---

## 2. Evidence Status

| Status | Definition |
|---|---|
| Not Requested | Evidence has not yet been requested |
| Requested | Evidence request has been submitted |
| Received | Evidence has been received |
| Under Review | Evidence is being assessed |
| Accepted | Evidence is sufficient for the requirement |
| Partially Satisfactory | Evidence provides some assurance but additional information is required |
| Exception | Evidence identifies a control deficiency |
| Not Applicable | Requirement does not apply and justification has been accepted |

## 4. Evidence Prioritization

Because CloudServe is classified as a Tier 1 vendor with Critical inherent risk, evidence requests are prioritized according to their potential impact on the assessment.

### Critical Priority

Critical evidence should be obtained and reviewed before final vendor approval.

Examples include:

- Independent security assurance
- Privileged access controls
- Data inventory and data flows
- Encryption controls
- Penetration testing
- Incident response
- Business continuity and disaster recovery
- RTO/RPO
- Data Processing Agreement
- Subprocessor inventory

### High Priority

High-priority evidence provides additional assurance over significant security and operational controls.

Examples include:

- Security policies
- Vulnerability management
- Secure SDLC
- Security monitoring
- Privacy governance
- Fourth-party governance
- Access review procedures

### Medium Priority

Medium-priority evidence supports the overall assessment but may not prevent progression where adequate alternative evidence exists.

Examples include:

- Log retention documentation
- Privacy rights procedures
- Supporting operational procedures

## 5. Evidence Review Criteria

Evidence should be evaluated using the following criteria:

### Relevance

Does the evidence directly relate to the control or risk being assessed?

### Currency

Is the evidence sufficiently current to provide meaningful assurance?

### Scope

Does the evidence cover the services, systems, locations, and data relevant to FinServe?

### Completeness

Does the evidence adequately demonstrate how the control operates?

### Independence

Where appropriate, has the control been independently assessed?

### Exceptions

Does the evidence identify material findings, limitations, exclusions, or exceptions?

---

## 6. Evidence Quality Rating

Evidence quality will be assessed using the following scale:

| Rating | Interpretation |
|---|---|
| Strong | Current, relevant, complete, and independently supported |
| Adequate | Provides reasonable assurance with minor limitations |
| Limited | Provides partial assurance or has significant limitations |
| Insufficient | Does not adequately demonstrate control effectiveness |
| Unavailable | Required evidence has not been provided |

## 8. Evidence Exceptions

Where requested evidence cannot be provided, the exception should be documented rather than automatically treated as a failed control.

The assessment should determine:

1. Why the evidence is unavailable.
2. Whether alternative evidence can be provided.
3. Whether the underlying control exists.
4. Whether the limitation creates additional risk.
5. Whether compensating controls exist.
6. Whether remediation is required.
7. Whether formal risk acceptance is necessary.

---

## 9. Evidence Handling and Confidentiality

Vendor evidence may contain confidential or sensitive information.

In a production GRC environment, evidence should be stored in an appropriately secured repository with access restricted to authorized personnel.

For this portfolio case study, sensitive vendor evidence is **simulated** and no confidential third-party information should be uploaded.

Where example evidence is created for demonstration purposes, it should be clearly labelled:

**SIMULATED / PORTFOLIO DEMONSTRATION — NOT ACTUAL VENDOR EVIDENCE**
